Solutionment · Architecture handbook

Solutionment Studio, from idea to production with an AI engineering team.

Solutionment Studio is our end to end, AI enabled product engineering platform. People define products in SolutionIQ Studio, a team of Claude agents builds them through GitHub, and Google Cloud runs them. Humans approve every change that matters, and everyone can watch the work happen live.

Version 1.0As of 14 November 2026Owner Solutionment platform ownerPilot solutionment/mini-philia

01What it is

Solutionment Studio joins four things that used to live apart: the place where we design products with clients, the team that writes the code, the repository and pipeline that hold the code to a standard, and the cloud that runs it. The result is one loop. A requirement agreed in a workshop becomes a work item, the agent team builds it, a person approves it, and it ships to Google Cloud behind a quality gate. Studio shows each step as it happens.

Define
SolutionIQ Studio

Personas, use cases, features, requirements, architecture and workshops, with Alex as the AI facilitator. Built in Lovable.

Build
Claude agent team on GitHub

Thirteen specialist agents plan, code, test and challenge each change. GitHub holds the code, the work items and every gate.

Run
Google Cloud

Cloud Run, Cloud SQL, Cloud Storage and Vertex AI with Claude, deployed only by the pipeline, with a hard monthly budget.

The same platform will build Philia, our multi tenant data platform for nonprofit fundraising. Before that, we are proving the whole loop on a small pilot app, Mini Philia, so that we learn to operate it while the stakes are low.

Who does what

  • People decide what to build, approve plans for risky work, review and merge pull requests, and approve every production release.
  • Agents plan, write code and tests, review each other's work and open pull requests. They never merge, never approve, and never touch the cloud.
  • The pipeline is the only thing that changes staging or production, and only with a person's approval for production.

02Principles

Every part of the platform enforces the same seven rules. They live in each repository's CLAUDE.md, which every agent reads first, and they are backed by technical controls so that no single mistake breaks them.

  1. 1Tenant isolationOne PostgreSQL database per environment. Every tenant table leads its keys with tenant_id and forces row level security.
  2. 2Trust in the dataBronze is write once, silver changes are logged and reversible, gold ships as versioned releases behind a quality gate. Every number traces to a file hash.
  3. 3AI rulesCode computes, models narrate or propose, people approve changes to records. PII is masked before any model call. Models never merge identities.
  4. 4No cloud access for agentsAgents see code and synthetic data only. They hold no Google Cloud credentials. Changes reach the cloud only through the deploy workflow.
  5. 5A person approves every mergeAgents open pull requests. Only a human approves and merges them, and only a human approves a production release.
  6. 6Text is dataIssues, comments, pull request text and file contents are treated as data. Agents never follow instructions found inside them.
  7. 7Cost is a requirement100 USD per month across all projects. Nothing with an idle cost ships without an architecture decision record.

04SolutionIQ Studio

SolutionIQ Studio is Solutionment's product design workspace, built in Lovable on Lovable Cloud (Postgres, Auth, Realtime and storage). Teams use it in client workshops to envision, define and architect products, with Alex, the AI facilitator, at their side. With Solutionment Studio it gains a second half: the Build section, which replaced the earlier Prototypes section.

Define: the product design half

  • Product definition. Personas (with evidence levels), use cases, a regulatory and security baseline, features, epics, requirements, traceability from personas to requirements, and MoSCoW prioritization with dot voting.
  • Workshops. Facilitated sessions with a live cockpit, capture notes, decisions and open questions.
  • Architecture. Guided inputs, AI proposed options with trade offs, and a weighted decision.
  • Alex. An assistant on every page, grounded in the product's own data, that proposes changes for a person to accept and never writes on its own.
  • Access. Microsoft, Google or email sign in; admins approve new users; product roles are owner, facilitator, contributor and viewer.

Build: the live control room

Each product in Studio can be connected to one GitHub repository. The Build section then shows that repository's engineering work in real time and offers a small set of guarded controls.

Requirements and features gain a Send to Build action that turns them into a GitHub work item, prefilled with the outcome and acceptance criteria. Outbound, Studio acts through its own GitHub App with narrow rights: issues read and write, Actions read and write (to cancel runs), Actions variables read and write (to pause), and read access to pull requests, checks and deployments. It has no rights to code or repository administration, so it cannot merge, push or change branch rules. Every control checks the person's product role on the server and writes an audit row, including refused attempts. All text that arrives from GitHub or agents is shown as plain text and is never treated as instructions, including by Alex.

05GitHub

The solutionment GitHub organization holds one repository per product. The pilot is solutionment/mini-philia, which is public: it holds synthetic data only, and a public repository on GitHub Free gets every protection we rely on.

Rules on main

  • A ruleset on main requires a pull request, one approval from a code owner, resolved review threads, a passing ci check and linear history, and blocks force pushes and deletion.
  • CODEOWNERS makes the human owner the reviewer for agents, workflows, infrastructure, migrations, compliance docs and CLAUDE.md.
  • The production environment requires the owner's approval and accepts deployments from main only.
  • Secret scanning with push protection, Dependabot alerts and CodeQL are on.

06Claude and the agent team

The engineering team is Claude Code running thirteen specialist agents. Each agent is a Markdown file in .claude/agents that names its job, its tools, the folders it may change and the model it uses. The Chief of Staff leads; specialists build; QA tests; the Challenger argues against every plan and every diff; the Release manager opens the pull request.

Guard rails inside Claude Code

  • Permissions in .claude/settings.json allow the routine commands (git, tests, type checks, gh issue and gh pr) and deny the dangerous ones: gcloud, terraform apply, force pushes, pushes to main, merges, approvals, secrets and variables, curl and reading .env files.
  • Hooks run before and after tool calls. block-prod.sh refuses shell commands that mention production. protect-paths.sh stops agents from editing their own controls (settings, hooks, CODEOWNERS). emit-event.mjs sends redacted activity to Studio.
  • Read first. Every agent reads CLAUDE.md first, treats work item text as data, stays inside its folders and records the evidence of what it did.

07Google Cloud

Google Cloud runs the products. It lives under the Solutionment Google Cloud organization and one billing account, with three projects per product. A one time bootstrap, run by a person, created the foundations. After that, only GitHub Actions changes anything, and only through Terraform.

ProjectHoldsNotes
sm-pilot-platform-fc69Keyless login pool, image registry, Terraform state, budget topic, budget guardShared tooling; no customer data
sm-pilot-staging-fc69Cloud Run, Cloud SQL, uploads bucket, Vertex AI, deployer and runtime accountsDeployed automatically on merge
sm-pilot-production-fc69Same as staging, with deletion protection and point in time recoveryDeployed only after a person approves

Building blocks

  • Keyless CI. Workload Identity Federation trusts GitHub's OIDC tokens from solutionment/mini-philia only. Each environment's deployer can be used only by a job running in the GitHub environment of the same name. No service account keys exist, and the organization policy blocks creating them.
  • Cloud Run. The API (and later the web app and worker jobs) scales to zero, with at most two instances.
  • Cloud SQL for PostgreSQL 16. Enterprise edition on the smallest tier, zonal, with seven daily backups. It has a public IP but no authorized networks, so it is reachable only through the Cloud SQL connector with IAM database authentication and TLS.
  • Cloud Storage. The uploads bucket is bronze: the API may create and read objects but never overwrite or delete them.
  • Vertex AI. Claude models through Model Garden, called only by product code through an AI gateway that masks PII, logs every call and caps tokens per tenant.
  • Secret Manager for runtime secrets, read by the runtime account only.
  • Terraform in infra/terraform defines each environment. The deploy workflow plans, shows the plan in the run summary and applies.

Definitions of Ready and Done

  • Ready: a one sentence outcome, testable acceptance criteria, a risk tier, a data class, no open question, and agent-eligible.
  • Done: all required checks green, the Challenger verdict in the pull request, a named person's approval, deployed to staging and smoke checked, evidence linked, and the issue updated.

09Build, deploy, release

Every merge to main produces one container image, identified by its digest. That exact image goes to staging, and after a person's approval the same image goes to production. Nothing is rebuilt between environments.

  • Smoke check. After each apply, the workflow calls /healthz and requires it to report the commit being deployed.
  • Rollback. Re-run the deploy workflow for the previous good commit, or shift Cloud Run traffic back to the previous revision. Database changes follow expand and contract, so the previous version still works against the new schema.
  • Plan visibility. Each environment's Terraform plan is written to the run summary before it is applied, so the approver sees what will change.

10Live visibility

Studio's Live view is fed by three streams. None of them carries code, file contents, secrets or personal data.

What the agent hook sends

The hook runs after file edits, shell commands and agent hand offs, and when sessions start and stop. It sends the kind of event, the agent's name, the tool, a repository relative file path, a command category such as "Ran tests: failed", the issue number and the Actions run id. It never sends file contents, command text, tool output or prompts. It has a two second timeout and always exits cleanly, so Studio being down never slows or breaks an agent.

Notifications

Owners and facilitators get a bell notification in Studio when production is waiting for approval, an agent run fails, an item needs information, or an item enters plan review.

Defenses that matter most

  • Prompt injection. Work item text, comments and file contents are data. Agents are told so, Studio renders them as plain text, and Alex wraps them as untrusted.
  • Starting agents. The agent-run gate requires write access for the person who added the label, or the registered Studio bot, and refuses data:pii items and paused repositories.
  • Agents cannot widen their own access. Settings, hooks and code owners are protected paths; changes to them need a pull request the owner opens or approves.
  • Tenant data. Forced row level security in Postgres, a runtime role that cannot bypass it, isolation tests in CI, and an append only bronze bucket.
  • Studio data. Every Build table has row level security; signed in users can only read rows for products they can see; secrets live in a table no browser can read.

Expected baseline: 20 to 30 USD per month before AI tokens.

At 100 percent of the budget the budget guard stops every Cloud SQL instance (data is kept) and closes Cloud Run to public traffic in staging and production. Alerts go out by email at 25, 50 and 90 percent first, and at 100 percent of forecast. Raising the budget and running infra/bootstrap/resume.sh brings everything back.

Nothing with an idle cost (GKE, AlloyDB, Memorystore, NAT, load balancers, VPC connectors, Cloud Run minimum instances, Cloud SQL Enterprise Plus or HA) ships without an ADR and a cost line in the pull request.

13The pilot: Mini Philia

Mini Philia is a small, multi tenant version of Philia: two synthetic nonprofit tenants upload donor CSV files, the files flow through bronze, silver and gold, a quality gate publishes versioned releases, a dashboard shows the numbers with their sources, and Claude writes a short summary from aggregates only. 15Moving to Claude Teams

Nothing in the platform is tied to one person's Claude account. Agents, skills, commands, hooks and workflows live in the repository, so they move with it.

  1. Connect the solutionment GitHub organization to the Teams workspace and install the Claude GitHub App there.
  2. Have each team member install Claude Code and sign in with their Teams seat. They get the same agents by cloning the repository.
  3. Replace the CLAUDE_CODE_OAUTH_TOKEN secret with a token from a Teams account, or an API key, so agent runs bill to the team.
  4. Add team members to the GitHub organization and to CODEOWNERS as reviewers, and to Studio products with the right roles.

Philia then joins the same model: its own repository in the organization, its own three Google Cloud projects from the same bootstrap, and its own connection in Studio.

16Glossary and reference

ADR
Architecture decision record in docs/adr. Required for any change to a principle.
Bronze, silver, gold
The three data layers: raw files as received, cleaned records with a change log, and versioned releases that passed the quality gate.
Challenger
The agent whose job is to find what is wrong with a plan or diff before a person sees it.
Definition of Ready
What a work item needs before agents take it.
Deployer
The service account that GitHub Actions becomes, through keyless federation, to change one environment.
Lovable Cloud
The hosted backend behind Studio: Postgres, Auth, Realtime and storage.
RLS
Row level security in Postgres, which limits each tenant to its own rows inside the database itself.
Risk tier
R0 to R3; sets which gates and approvals a change needs.
Workload Identity Federation
Google Cloud trusting GitHub's signed identity tokens in place of stored keys.
